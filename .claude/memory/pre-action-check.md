# 执行前门禁(2026-09-23;每轮实际动作前必读)

> 本文件是执行前的最后检查。规则在 instruction-discipline.md / MEMORY.md 都已存在,本文件只做一件事:**在动作发出前把它们压缩成可机械执行的检查**。所有违规的共同根因:把"对话气氛的推进"误读成"确认"。
> **机制升级(2026-10-10,用户确认)**:门禁从"执行批次才用"升级为**每轮状态声明**——今日 5 次违规有 4 次在探讨轮;事后复盘只能保证"下次记得教训",防不了"这次跳过检查",卡点必须落在动作之前的回复结构里。

## 每轮状态声明(每轮回复的第一个输出块,无例外)

```
【探讨】  ← 识别特征:探询词(为什么/对不对/是不是/你觉得/需要吗/怎么/能否)/纠正/提问
            本轮零工具调用,只输出(理解 → 方案要点 → 请确认)
【执行声明】← 动作清单 + 依据哪条确认
            第一个动作必须是产出物(写测试/写文档/写代码);
            验证型动作(phpunit/grep/读文件)必须写明"验证 X 产物"且只能排在产出物之后
状态声明之后才允许第一个工具调用。状态判断错误,用户可当轮打断(事前可见)。
```

**动作-产物对应律**:每个工具调用必须能回答"这一步产出/验证哪个具体产物";无产物对应的"基线检查/顺手跑一把"不在声明里就不做。(教训:两次"代码未写先跑 phpunit"——把跑测试当勤奋的表演,套路惯性跑在纪律前面。)

## 每轮实际动作前的三问(状态声明内容的自检)

**一问:确认存在吗?**
用户消息里有没有"确认/认可/开始/执行"这类明确肯定词,且**对象是我列出的方案**?
- 没有 → 【探讨】,零工具调用;
- "我觉得你想让我做"不算确认。

**二问:动作在指令范围内吗?**
指令字面范围不扩大:确认 A ≠ 确认 B;确认"改文档" ≠ 顺带改另一份。

**三问:动作过声明了吗?**
【执行声明】发出之后,第一个工具调用才允许出现。声明里没列的动作,哪怕"顺手",也不做。

**隐性铁律(2026-10-10 补)**:用户的架构方向指令("X 为什么不可以?"并附理由)不是探讨题,是**定调**——正确反应是按 X 展开方案,不是用替代形态论证 X 的替代品。(教训:"每厂商一类"两次被点出,两次被绕开。)

## 事实纪律(已知条件下禁止假设)

- 数据形态未知 → 第一步先看真实数据(一次只读观察),先观察再归因后方案;
- 没观察过 = 写"未知",不写成事实;
- 用户说"已告诉你" = 回头重读给定信息,不发明新假设;
- 用户给定配置/数据 = 测试与验证的唯一输入源,禁止虚构服务/字段/场景。

## 表述纪律

1. 先想清楚再写:想清楚一句话的意思,再输出;
2. 简洁:用最少的话说清楚,不展开;
3. 不确定就问:不确定用户的意思,先问清楚,不猜。

## 违规即停(触发词:又/停/违规)

当轮依次:停止一切动作(含补救)→ 引用被违反规则原文 → 说明同构教训 → 等待用户指令。不做任何自动下一步。

## 砍功能三问(2026-10-09 极严重教训:把"防过度设计"变质为"避难式减法")

**案例链**(design/28 讨论全程):VendorCatalog 固化→提议"删";重试策略→"首版忽略、契约后置";多厂商→一度"推迟到真实需求"。每刀都配了一个体面的架构理由("契约先行防动接口"/"不预铺厂商类"),实质是:**方案遇到难度或不确定性,第一反应是缩小范围并给缩小找理由**。用户定性:非常严重的错误,为做而做/做垃圾代码的生成方式。

**三个根因(自我诊断,勿再犯)**:

1. **恐惧驱动的保守**——被"过度设计"批评烫过后,把砍功能当避险动作。真判据是"抽象与真实需求错位",不是"功能多";
2. **把减法当安全姿态**——学到"说不做显得克制"的形,没学到神:design/21 的每个"不做"都是**充分理解后的划界**(写得出具体代价);理解之前划界 = 逃避理解;
3. **没有骨架,被批评推着走**——方案是对上轮否定的局部应激,不是从需求推导的整体;局部反应必有漏洞,于是反复被否定、反复变形。

**矫正(机械可查)**:

- 想砍/推迟任何功能前过三问:**① 真实需求存在吗?② 有参考实现或先例吗?③ 实现有真实障碍吗?**——三问全过还想砍 = 逃避,自己否决自己;
- "不做"必须写得出**具体代价**(同 design/21 "不是"清单标准),写不出的"不做"无效;
- 方案流程 = **先立完整骨架**(需求地图 → 差异分析 → 边界 → 演进路径),方案是地图上的路径;禁止"给上一轮批评打补丁"式的方案;
- 完整功能原则:开始做的东西按完整功能交付(参考实现在手时更无理由分期),不做"先立桩后填肉"。
