# 文档质量考评机制(用户要求沉淀,2026-10-30)

> 来源:双语文档工程(D0–D3)完成后,用户要求"对生成文档的内容质量打分"——自评 8/10(真实性 9 / 结构 9 / 使用助益 7),并发现 3 处真实缺陷。本文件沉淀**可复用的考评机制**,之后任何成批产出的内容(文档/示例/教程)都按此自查。

## 评分维度(三项加权)

| 维度 | 权重 | 检什么 |
| --- | --- | --- |
| **真实性** | 最重(一票否决项) | 每个出现的 API(类/方法/参数默认值/CLI 标志/文件名)经 grep `src/` 实测;**示例是高危区**——最容易写进"看起来合理的幻觉 API" |
| **结构完整性** | 中 | 声明的模板逐篇核对(如五节结构);索引条目与文件一一对应;链接全站可达 |
| **使用助益** | 最难自评 | 写的人说了不算;缺"从零到第一次成功"的贯通叙事、排障指南(症状→原因→修法)即扣分 |

## 已验证的自查方法(次序即流程)

1. **抽检幻觉 API**(最有效):对文档里**每一个**构造/静态调用,`grep -rn` 源码核对签名。本次即抓到 `ValueResult::of()`(真实是 `got()`/`pending()`/`missing()`)——写文档时的"合理推测"正是幻觉 API 的温床;
2. **结构核对脚本化**:五节结构逐篇数 `^## ` 数量;索引行 vs 文件数比对;配对不变量(每语言目录同模块集)机械校验;
3. **全站链接校验排除行内码**:先剥 backtick 内内容再抽 `](...)` 链接——否则规范文件里的"模式示意"会被误判为断链;
4. **读者旅程走查**:把自己当第一次接触的开发者走一遍——"5 分钟内能不能跑通第一个东西?出错了能不能自己查?"——贯通叙事与排障表是这一步才暴露的缺口。

## 结构性教训

- **我上轮给分时差点犯的错**:把"已生成 32 个文件"当作反对重构的论据(平铺 vs 分目录之争)——**既成事实不是论据,未来维护成本才是**。加语言/加模块的可扩展性 > 眼下挪文件的麻烦;
- **量化基准**:每篇手册 150–250 行;双语工程 = 2× 内容 + 配对/索引/校验三件套;自查四步全程约 15 分钟,产出 3 类真实缺陷,值得;
- **8→9 分的路径**:修幻觉 API、补齐结构、加 getting-started贯通教程 + 排障表;**最后 1 分只有真实使用者反馈能挣**——写作者自评上限就是 9。

## 触发时机(之后何时用此机制)

- 任何成批文档/示例/教程生成后(如本次 D2/D3);
- 大型功能交付后为其补写的使用文档;
- 长期未维护的文档"复检"(配对不变量 + 链接校验脚本可直接复用)。
