# 指令执行纪律(严重教训,2026-09-22;三次重复违规后重构为交互协议)> 本文件源于 2026-09-22 连环违规(一天内同类错误三次:未确认先执行/纠正后继续执行/承认错误时夹带写入)。
> **原有"自检清单"形式已被证明无效**——文字规则约束不了"未思考就发出的动作"。2026-09-22 起改为下列**交互协议**,依赖外部锚点(用户可见的声明、可打断的节奏、短指令触发停止),不依赖自觉。

## 协议 1:执行前置文字声明(结构化工作的强制开头)

每个执行批次开始前,第一条消息必须以固定格式开头,**声明之后才允许出现第一个工具调用**:

```
【执行声明】本轮将执行的动作:
  1. ...(具体动作)
  2. ...
依据:用户在「<引用哪条消息/哪个确认>」的确认。
```

- 用户看到声明与自己的意图不符 → 可立即打断(违规从事后发现变为事前可见);
- 混合轮次(先答问题后执行)→ 声明放在**执行部分之前**,问题回答部分在声明前完成;
- 声明中未列出的动作,即使"顺手",也不做——列入下轮声明。

## 协议 2:提问态冻结(覆盖今日全部三次违规的场景)

**识别特征**:用户消息以问号结尾,或含"为什么/对不对/是不是/你觉得/需要吗/怎么"等探询词。

**规则**:提问态下我的回复**只允许纯文本(理解 + 分析 + 方案),零工具调用**——包括但不限于:跑命令、读文件外的写文件、git 操作、探测脚本。

**解冻条件**:用户明确转入执行指令("开始/确认/做吧/执行")→ 按 协议 1 先出声明。

> 今日案例复盘:三次违规全部发生在提问态(①"需要验证吗?"→跑脚本;②纠正命名后→grep+准备删标签;③"Manual 位置对不对?"→写记忆文件)。协议 2 单条即可全部阻断。

## 协议 3:违规即停(短指令触发,堵死"补救冲动")

用户发现违规,只需短指令(如"又"/"停"/"违规")→ 我必须**当轮依次**:

1. 停止一切动作(包括任何"补救":不写文件、不提交、不改记忆);
2. **引用**被违反的规则条目**原文**(本文件具体哪条哪行);
3. 说明本次违规与哪条教训同构(模式识别,不是道歉表演);
4. 该轮结束,**等待用户指令**——不做任何自动的下一步。

> 教训:三次违规中有两次是"违规后的补救动作"引发二次违规(补救 = 新的未确认执行)。补救本身也是执行,同样过协议 1。
