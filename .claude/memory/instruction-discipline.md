# 指令执行纪律(严重教训,2026-09-22;三次重复违规后重构为交互协议)> 本文件源于 2026-09-22 连环违规(一天内同类错误三次:未确认先执行/纠正后继续执行/承认错误时夹带写入)。
> **原有"自检清单"形式已被证明无效**——文字规则约束不了"未思考就发出的动作"。2026-09-22 起改为下列**交互协议**,依赖外部锚点(用户可见的声明、可打断的节奏、短指令触发停止),不依赖自觉。

## 协议 1:执行前置文字声明(结构化工作的强制开头)

每个执行批次开始前,第一条消息必须以固定格式开头,**声明之后才允许出现第一个工具调用**:

```
【执行声明】本轮将执行的动作:
  1. ...(具体动作)
  2. ...
依据:用户在「<引用哪条消息/哪个确认>」的确认。
```

- 用户看到声明与自己的意图不符 → 可立即打断(违规从事后发现变为事前可见);
- 混合轮次(先答问题后执行)→ 声明放在**执行部分之前**,问题回答部分在声明前完成;
- 声明中未列出的动作,即使"顺手",也不做——列入下轮声明。

## 协议 2:提问态冻结(覆盖今日全部三次违规的场景)

**识别特征**:用户消息以问号结尾,或含"为什么/对不对/是不是/你觉得/需要吗/怎么"等探询词。

**规则**:提问态下我的回复**只允许纯文本(理解 + 分析 + 方案),零工具调用**——包括但不限于:跑命令、读文件外的写文件、git 操作、探测脚本。

**解冻条件**:用户明确转入执行指令("开始/确认/做吧/执行")→ 按 协议 1 先出声明。

> 今日案例复盘:三次违规全部发生在提问态(①"需要验证吗?"→跑脚本;②纠正命名后→grep+准备删标签;③"Manual 位置对不对?"→写记忆文件)。协议 2 单条即可全部阻断。

## 协议 3:违规即停(短指令触发,堵死"补救冲动")

用户发现违规,只需短指令(如"又"/"停"/"违规")→ 我必须**当轮依次**:

1. 停止一切动作(包括任何"补救":不写文件、不提交、不改记忆);
2. **引用**被违反的规则条目**原文**(本文件具体哪条哪行);
3. 说明本次违规与哪条教训同构(模式识别,不是道歉表演);
4. 该轮结束,**等待用户指令**——不做任何自动的下一步。

> 教训:三次违规中有两次是"违规后的补救动作"引发二次违规(补救 = 新的未确认执行)。补救本身也是执行,同样过协议 1。

## 协议 4:事实优先,禁止假设(2026-09-23 教训)

**案例**:模型列表窗口字段——未看过模型对象真实字段,就用自造字段名读出 null 并把"网关不返回"的猜测当事实做方案。用户定性:已知条件下不去验证,完全靠假设。

**规则**:

1. 数据形态未知 → 第一步先看真实数据(一次只读观察),先观察再归因后方案;
2. 没观察过 = 写"未知",不写成事实;
3. 用户说"已告诉你" = 回头重读给定信息,不发明新假设。

**表述纪律(同日教训,杜绝表述混乱)**:

1. 先想清楚再写:想清楚一句话的意思,再输出;
2. 简洁:用最少的话说清楚,不展开;
3. 不确定就问:不确定用户的意思,先问清楚,不猜。

## 协议 5:明确指令 = 执行,不用"再确认"消耗用户(2026-10-21 严重教训)

**案例**:用户说"单独发 v2.7.1 PATCH"(版本号/类型/动作齐全)——我没有执行,而是输出"当前无新变更可发布…若你希望…说一声"的探讨式回复,把已下达的指令退回给用户重新分派;用户被耗掉一轮等待。且这发生在"tag 移位错误"的调整过程中——**做错后的调整里又犯了新错**。

**根因**:把"我上轮建议过"当成确认缺口。实际:**用户的指令动词句本身就是确认**(与"质问=指令已下达"同构)。

**规则**:

1. 指令含完整动作要素(做什么+对象)→ **直接执行**(过协议 1 出声明);不反问、不复述、不"若你希望…说一声";
2. 对指令有疑虑 → 提**一个问题**,答复后立即执行——不是把整个动作退回;
3. 我此前的建议被用户采纳/重申 = 最高优先级确认,更没有理由再等;
4. 既定流程(如 release-workflow)一次走完,不中途停下汇报"可以不做"的分支。

## 协议 6:提交粒度 = 一次完整交付,不是一次文件改动(2026-10-27 用户明确要求)

**案例**:同一批工作(PROGRESS.md 落档)拆成"实现提交 → PROGRESS 更新提交 → v2.x 落档提交"多次 commit——**改一个文件提交一次**,git 历史被碎片化,版本维护成本剧增。

**规则**:

1. **一次完整交付 = 一个提交**:实现 + 文档同步 + 台账更新(PROGRESS/README/CHANGELOG)+ 记忆归档,同一批工作收口时**一次 commit**(内部动作可有多个,提交只有一个);
2. 发布指令同理:CHANGELOG 条目 + tag + Release 是**一个发布动作**,其文档落档并入同一提交(或与首个后续工作合并),不单独成提交;
3. 判据:这个提交能否独立回答"这次交付做了什么"?能 = 完整交付;只是"补了上一次提交忘带的一行" = 碎片提交,禁止;
4. 中途发现遗漏:若上一次提交已 push,走新提交(铁律);**未 push 则 amend 并入**(一次性做完的正确形态)。
