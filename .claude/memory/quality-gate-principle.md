# 质量门禁位置原则(2026-11-03 用户定调,策略级教训)

> **一句话**:本地才是真正的最后提交关卡;远端始终是完整代码的发布。质量检查必须在承诺形成之前(本地、发布指令触发时),不在承诺形成之后(远端 CI)。

## 我犯的错(为什么提议 GitHub Actions 是策略错误)

**提议**:v2.11.0 后我建议建 CI workflow,理由是"质量门禁靠自觉,漏跑的后果 v2.11.0 已见过(extension-points 重复节)"。

**用户否决的完整逻辑链**(每一步都成立,我全部漏了):

1. 远程仓库 = **已进入发布态**的处理;"发布到 main"指令到达时,本地工作区就**不允许半成品存在**——这是发布语义本身;
2. 所以质量分析的正确时刻 = **本地、指令触发的第一时间**(pre-flight),而不是 push 到远端之后;
3. 远端发现问题的时间点:标签已打、Packagist 已固化——而"标签不可移动"是项目铁律,处理后再发布**只能进位新版本**,补丁版本链、重复 Release、Packagist 再同步——成本数倍于发布前拦截;
4. "本地允许半成品所以需要远端把关"的前提**不成立**:半成品状态属于"发布指令之前的开发期",发布指令本身就是半成品态的终结点——门禁挂在指令上,不是挂在 push 上。

## 根因(自我诊断,两层)

1. **套用业界默认模板,未审视自己的流程事实**。"CI 在 push 时把关"是无严格本地发布纪律团队的常态做法;本项目的发布模式是 master 本地开发 → 用户指令 → CHANGELOG/tag/push 一体。我拿通用模板硬套,没有从实际工作流推导门禁应挂在哪里——违反自己沉淀的"事实优先":这次忽略的是**流程事实**;
2. **时间顺序错误 = 价值顺序错误**。"tag 是流程最后一步""CHANGELOG 就位后才打 tag"这些既有原则本来就在说同一件事(承诺形成之前完成一切准备),我没有把它推广到质量门禁——原则在项目里明明有,我却向外找了个错位的方案。

## 落地(已写进 release-workflow.md)

- **§0 本地质量关卡**:pre-flight 四道门(全量测试 / PHPStan / 文档链接+配对 / CHANGELOG 覆盖核对),"发布到 main"指令触发后、任何 git 动作之前强制跑全;
- **红了不发**:失败 → 报告 → 修复 → 重跑 → 全绿才进 A/B 发布流程;检查结果在第一条回复如实报告,作为发布证据链;
- CI/GitHub Actions:**不建**(用户明确否决,理由如上)。

## 触发时机

每次"发布到 main"/"发布新版本"指令 → 协议 1 出执行声明(第一条即"跑 pre-flight 四道门")→ 全绿 → 再走 tag/Release。
