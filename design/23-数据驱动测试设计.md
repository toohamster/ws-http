# 23 数据驱动测试设计(Automated\Dataset 子模块)

> 层归属:**functional 层内子命名空间 `Ws\Http\Automated\Dataset\`**(不是顶层组件,判据见 §1.2)。使用者:批量回归测试作者(数据驱动场景)、CI 编排者。
> 背景:同一场景需要对一组测试数据(如 N 个用户)各完整跑一遍,按组维度汇总成功/失败。当前引擎(design/16 Runner)只支持单次运行,缺数据驱动形态。
> 与 design/22(pause/凭据注入)的关系:**正交、互不依赖**——22 解决"场景中途缺一个值",23 解决"场景开始前备好整组输入、按记录迭代"。

**简单路径**(场景作者视角,内联数据):

```json
{
  "settings": { "iterate": "users" },
  "datasets": {
    "users": [
      { "username": "u1", "password": "p1" },
      { "username": "u2", "password": "p2" }
    ]
  },
  "steps": [
    { "type": "http", "name": "login",
      "request": { "method": "post", "url": "https://api.example.com/login" },
      "body": { "form": { "username": "${username}", "password": "${password}" } } }
  ]
}
```

```bash
vendor/bin/ws-http run scenario.json --dataset users.json   # 外部文件覆盖/提供数据集
```

> 每条记录独立完整跑一遍场景,`${username}` 等字段即普通变量;Report 出组维度汇总。

## 1. 定位与边界

### 1.1 是什么

1. **datasets 声明**:场景内定义一或多组记录数组(内联/文件/自定义 Loader);
2. **iterate 执行**:指定某一数据集,Runner 外层套**迭代循环**——每条记录注入 VariableScope(记录字段即变量)后完整执行一次场景;
3. **batch 级 Report**:汇总总数/成功/失败/失败记录索引,挂载每条记录的子 Report。

### 1.2 为什么不是顶层组件(评审决策记录)

曾评估上升为与 NanoGpt 同级的顶层组件(`Ws\Http\Dataset\`),否决,理由是两者归属判据相反:

| 判据 | NanoGpt(可独立) | Dataset(必须住引擎内) |
| --- | --- | --- |
| 依赖面 | 只依赖公开 API(Plugin\OpenAI\Client) | **必须深入 Runner 内部**:每记录注入 VariableScope、每轮产出完整 StepResult 链、failFast 按单轮收窄 |
| 领域归属 | 新领域,无既有归属 | **就是自动化引擎的执行形态**,与顺序执行/failFast/Report 同域(design/16) |
| 侵入性 | 零(core/functional 不感知) | 拆出去则 Runner 需暴露迭代钩子/状态快照,公开面反而变大 |

落位 `Automated\Dataset\` 子命名空间已满足组件化收益的实质(独立文档/自包含目录/独立排期/CLI 与编程双入口);将来 Runner 若重构出更干净的迭代接口,再晋升顶层组件成本很低。

**不是**(防过度设计):

- 不做记录级并行(首版串行迭代,扩展预留);
- 不做数据集间依赖/参数化派生(如"用 u1 登录拿的 token 给 u2 用"——那是场景内 extract 的事);
- 不做数据源服务化(数据库直连等,Loader 契约留给使用者自定义)。

## 2. 契约

### 2.1 数据声明(Schema v2 追加)

```jsonc
{
  "datasets": {                                  // 可选;名字 → 数据源描述
    "users": [ {"username": "u1", ...} ],        // 形态 A:内联数组(直接是记录列表)
    "admins": { "file": "./admins.json" }        // 形态 B:文件(相对场景文件目录);也可 {"loader": "my-loader", ...}
  },
  "settings": {
    "iterate": "users"                           // 可选;要迭代的数据集名
  }
}
```

校验规则(追加 design/14 V 序列):

- **V14**:`datasets` 必须是对象,每个值是"数组或含 file/loader 的对象";
- **V15**:`settings.iterate` 引用的数据集名必须存在于 `datasets`;
- **V16**:`iterate` 存在时,数据集必须非空数组且所有记录为**同构 object**(键集一致;异构 → 402,防止变量集漂移);
- **V17**:`--dataset` CLI 覆盖的文件必须是"记录数组"且与被覆盖数据集同构。

### 2.2 Loader 契约(数据源注册点,独立于 design/22 的 ValueSource)

```php
namespace Ws\Http\Automated\Dataset;

interface DatasetLoaderInterface
{
    /** @return array<int, array<string, mixed>> 记录列表 */
    public function load(array $spec): array;      // spec = datasets 里的对象形态(file/loader 参数)
}

final class InlineLoader implements DatasetLoaderInterface  // 内联数组直通
final class JsonFileLoader implements DatasetLoaderInterface // file: 相对场景文件目录解析,JSON 数组

final class DatasetRegistry
{
    public function register(string $name, DatasetLoaderInterface $loader): void;  // 重名 420
    public function load(string $name, array $spec): array;                        // 未知名 421
}
```

> 注册点独立于 pause 的 ValueSource:一个面向"场景开始前的输入集",一个面向"场景中途取值",不合并。

## 3. DatasetRunner(执行模型)

```php
final class DatasetRunner
{
    public function __construct(Runner $runner);   // 复用既有单次运行 Runner,不改其内部

    /** @param array<int, array<string, mixed>> $records */
    public function run(Scenario $scenario, array $records, ?string $recordVar = null): BatchReport;
}
```

执行流程:

```
for each record(串行):
    scope = 新 VariableScope(基础变量) + record 字段逐个注入(记录字段可被场景内 extract 覆盖)
    report_i = runner->run(scenario, scope)          # 单轮完整运行,内部 failFast 语义不变
    batch 收集 report_i;单轮失败不中断批次
汇总 → BatchReport
```

要点:

- **failFast 收窄到单轮**:批次级永远跑完全部记录(这是数据驱动的本意);单轮内 failFast 行为与 design/16 一致;
- **记录字段与既有变量关系**:record 字段初始注入,场景内 extract/assert 产生的变量优先级更高(可覆盖);`recordVar` 可选,提供 `{"index": 0, "data": {...}}` 形态便于脚本内引用当前记录号;
- **迭代间隔离**:每轮全新 VariableScope(既有单次运行的隔离假设自然成立);CookieStore 是否跨轮共享由 settings 既有语义决定(默认每轮新开,`cookieJar: shared` 可共享——沿用 design/16 字段)。

## 4. BatchReport(batch 级报告契约)

```jsonc
{
  "kind": "batch",
  "dataset": "users",
  "total": 50,
  "passed": 47,
  "failed": 3,
  "failedRecords": [12, 30, 44],              // 记录索引(0-based)
  "failures": [                               // 仅失败记录,便于排查
    { "index": 12, "record": {"username": "u13"},
      "report": { /* 该轮完整 Report(design/16 契约) */ },
      "failedStep": "login" }
  ],
  "durationMs": 83210,
  "startedAt": "2026-09-17T08:00:00+08:00"
}
```

- CLI 输出摘要行:`Batch users: 47/50 passed, 3 failed (12, 30, 44) in 83.2s`,失败记录逐条列 failedStep + 首个失败原因;
- `--report out.json` 沿用既有机制,batch 模式写 batch 结构;
- 退出码:failed>0 → 非 0(CI 友好)。

## 5. CLI(design/16 CLI 规格追加)

```
vendor/bin/ws-http run scenario.json --dataset users.json
# --dataset <file>              用文件记录迭代执行(文件内数组即数据集,免改场景 JSON)
# --dataset-name users          --dataset 指向的记录注入到场景 datasets 的哪个名字下(默认 "_cli")
# --dataset-key users           场景内已有 datasets 时,用文件内容覆盖该名字的数据集
```

编程入口:`new DatasetRunner($runner)->run($scenario, $records)`。

## 6. 错误码(400–499 引擎段追加,与 design/22 共段不冲突)

| 码 | 含义 |
| --- | --- |
| 420 | Loader 注册重名 |
| 421 | 未知名 Loader / iterate 或 --dataset 引用不存在的数据集(装配期) |
| 422 | 数据集非法(空/记录非 object/异构,见 V16/V17) |

## 7. 测试要点

| 用例组 | 覆盖 |
| --- | --- |
| Loader | Inline 直通;JsonFile(相对路径/文件不存在/非法 JSON);Registry 注册重名 420/未知名 421 |
| 校验 | V14–V17 各形态 |
| DatasetRunner(mock HTTP) | 2 条记录 × 完整场景 → 每轮变量注入正确且**互不串**(第 2 轮读不到第 1 轮 extract 的值);单轮失败不中断;recordVar;记录字段被 extract 覆盖的优先级 |
| BatchReport | 全过/部分失败/全败的结构;failures 只含失败轮;durationMs 汇总 |
| CLI | --dataset 注入/覆盖(--dataset-key)/退出码 |
| 隔离 | DatasetRunner 不修改 Runner 内部行为(无 iterate 的场景经它跑 = 单轮运行,结果与直接 Runner 一致) |

## 8. 与既有设计的衔接与实施

- design/14(Schema):datasets/iterate 字段 + V14–V17;
- design/16(Runner/Report/CLI):DatasetRunner 为 Runner 的**外层包装**,Runner 单次运行契约不变;BatchReport 为新报告 kind;CLI 追加 --dataset 参数;
- design/22:正交,互不引用,可独立实施、独立排期;
- 实施顺序建议:22(pause)先(改动集中在 Runner 一个分支 + 一个注册表),23 后(新增外层包装 + 报告层),互不阻塞。
