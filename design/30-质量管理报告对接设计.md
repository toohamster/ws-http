# 30 质量管理报告对接设计(reporting 声明 + IssueSink)

> 层归属:跨层——场景契约(§2)与收尾求值(§3)归 **functional(Automated)**;Sink 接口与适配器(§4)归 **functional 侧独立子命名空间** `Ws\Http\Automated\Qm\`;CLI(§5)归 bin。使用者:场景脚本作者(声明失败意味着什么)、QA 流程编排者(配置 Sink 适配器)、CI 集成者。
> 背景:测试引擎的职责边界在"跑场景 → 产出结构化结果"。但真实 QA 流程需要失败流转到质量管理平台(Jira/GitLab/GitHub Issues)。本设计给这条链路一个**通用契约**:场景声明(作者表达)+ 引擎计算(报告增强)+ Sink 适配器(平台差异),**引擎全程零平台感知、零网络调用**。
> 决策记录(2026-11-04 用户确认):① 建单时机 = **场景彻底跑完后从报告转换创建**——过程中创建失败数据不完整且污染测试结果,执行完当场创建使引擎背平台适配与状态机;② 引擎只做**计算**(收尾时求值 reporting 声明写进报告),**发送**归独立转换命令;③ 创建给谁/分配给谁 = 适配器 + 配置,不在代码。

**简单路径**(三段,每段一行入口):

```jsonc
// ① 场景作者:声明"这个场景失败意味着一个 P1 缺陷"
{ "id": "scenario-001", "steps": [ ... ],
  "reporting": { "severity": "P1", "labels": ["booking"], "on": "failure" } }
```

```bash
# ② 跑场景(既有命令,零变化)——报告自动携带 issueIntent
php bin/ws-http run scenario.json --report-out report.json
```

```bash
# ③ 流程编排者:任何时候,从报告转换创建(可重跑、可人工审核后发)
php bin/ws-http issues report.json --sink gitlab --config qm.json
```

## 1. 定位与边界

### 1.1 职责链(三段式,引擎只占中段)

```
┌─ 场景声明 ─────────┐   ┌─ 引擎(执行时)──────┐   ┌─ Sink 适配器(转换时)──────┐
│ reporting 声明块    │ → │ 收尾求值 → Report     │ → │ 读 issueIntent + 平台 API   │
│ (失败意味着什么)    │   │ .issueIntent(零网络) │   │ (去重/分配/字段映射/发送)    │
└───────────────────┘   └─────────────────────┘   └───────────────────────────┘
```

### 1.2 不是什么(防过度设计,写具体代价)

- **引擎不做平台调用**:建单涉及去重(查平台已有 open issue)、限速、重试、凭据——全是**跨运行的平台侧状态**,进引擎则测试执行退出码语义被建单成败污染,且每个团队策略不同(易变产品决策);
- **不建通用"质量管理平台适配层"组件**:平台差异(端点/字段/认证/去重语义)太大,统一抽象 = 最大公约数 + 无尽配置项;只给**一个接口 + 配置驱动**,适配器是独立小类;
- **不做 step 级建单声明**:报告流转是**场景级**语义(一个场景失败 = 一个缺陷单元),step 级声明会把流程策略泄漏进执行流;失败步骤明细已在 StepResult,适配器可自由组装;
- **不做报表/看板**:渲染是消费端职责(design/16 §5.1 既定决策),本设计只加一种可消费的数据(issueIntent)。

## 2. 场景契约:reporting 声明块(Schema v2 追加,场景级可选)

```jsonc
{
  "id": "scenario-001",
  "reporting": {                          // 可选;缺省 = 无声明,报告不含 issueIntent
    "on": "failure",                      // 可选,默认 "failure";目前唯一合法值(always 列扩展预留,见 V24)
    "severity": "P1",                     // 可选,非空字符串(语义由使用团队定义,引擎不解释)
    "labels": ["booking", "night-run"],   // 可选,字符串数组;元素支持 ${var}(收尾求值)
    "component": "${serviceName}",        // 可选,字符串,支持 ${var}
    "title": "预订流程失败: ${scenarioName}" // 可选,字符串,支持 ${var};缺省由适配器生成
  }
}
```

- 与 settings/variables/outputs 同级——它是**场景元数据**(失败的责任属性),不是执行单元;
- 求值发生在**场景收尾**(所有步骤结束、变量终态确定后),`${var}` 引用的是终值快照(design/15 §5);
- secret 变量在 issueIntent 求值结果中同样脱敏(design/16 §3.3 规则复用——建单内容可能进第三方平台,脱敏必须前置)。

校验(追加 V 序列,design/14):

| # | 规则 | code |
| --- | --- | --- |
| V24 | reporting 必须为对象;on ∈ 当前合法集("failure");severity 为非空字符串;labels 为字符串数组;component/title 为字符串;未知字段拒绝 | 402 |
| V25 | labels/title/component 中的 ${var} 引用名符合变量命名规则(加载期静态检查;是否已声明与 V10 同策略——运行期未定义按空串处理并出 warning) | 402 |

## 3. 引擎收尾求值:Report.issueIntent(计算职责,零网络)

### 3.1 求值时机

`Report::finalize()`(design/16 §1.1 第 5 步)内,变量终态快照之后:

```
if 场景声明了 reporting:
    intent = {
      on: "failure",
      shouldCreate: (on === "failure" && report 失败) || (on === "always"),   // 计算判定
      severity / labels / component / title:  → ${var} 用终态快照替换(未定义变量→空串+warning)
      context: {
        failedSteps: [ { id, name, failReason, statusCode, durationMs } ... ],  // 失败步骤摘要(脱敏后)
        lastVariables: 变量终态快照(secret 脱敏),                                // 复现上下文
        scenario: { id, name },
        ranAt: finishedAt, durationMs
      }
    }
    report.issueIntent = (shouldCreate ? intent : null)   // 判定为不该建单时显式 null(区分"没声明")
```

### 3.2 契约形态(Report JSON 追加可选字段,向后兼容)

```jsonc
// report.json 追加(仅声明了 reporting 且判定应建单时出现):
"issueIntent": {
  "severity": "P1",
  "labels": ["booking", "night-run"],
  "component": "booking-api",
  "title": "预订流程失败: 夜点娱乐-预订流程",
  "context": {
    "scenario": { "id": "scenario-001", "name": "夜点娱乐-预订流程" },
    "failedSteps": [ { "id": "submit", "name": "提交订单", "failReason": "assertion failed: ...", "statusCode": 500, "durationMs": 134 } ],
    "lastVariables": { "token": "***", "ktvId": "KT001" },
    "ranAt": "2026-11-04T11:00:00+08:00",
    "durationMs": 439
  }
}
```

- **判定权在引擎**(shouldCreate),**执行权在适配器**——适配器拿到 shouldCreate=false(null)时无事可做,拿到 true 时自由决定怎么发;
- 报告消费端(渲染器/CI)不感知新字段照常工作(与 design/29 §3.2 同款兼容策略)。

## 4. Sink 契约与适配器

### 4.1 接口(单方法,与 ReportRendererInterface 同款最小形态)

```php
namespace Ws\Http\Automated\Qm;

final class IssueIntent            // Report.issueIntent 的 PHP 对象形态(readonly 值对象)
final class SinkResult             // created: int, skipped: int, errors: string[](平台侧结果摘要)

interface IssueSinkInterface
{
    /** 消费一份 Report(JSON 数组形态或对象),返回创建结果摘要;不应抛异常(错误进 errors) */
    public function publish(Report $report): SinkResult;
}
```

### 4.2 适配器:配置驱动,不写死平台语义

```php
final class GitLabIssueSink implements IssueSinkInterface   // 内建示例(1 个,示范接缝)
{
    public function __construct(array $config);   // endpoint/project/token/labels 映射/去重查找策略等
}
// GitHub/Jira 等 = 使用者实现 IssueSinkInterface(几十行,调平台 API)
```

**配置文件**(使用者提供,`--config qm.json`),适配器自定义 schema,以 GitLab 示例:

```jsonc
{
  "endpoint": "https://gitlab.example.com/api/v4",
  "projectId": "42",
  "token": "${env:GITLAB_TOKEN}",           // 支持环境变量引用,凭据不入库
  "dedup": { "strategy": "search-open", "labels": ["auto-test"] },   // 去重:按标签搜 open issue,同标题跳过
  "assignee": "qa-team",                    // 分配——策略归使用者
  "labelMap": { "P1": "priority::high" }    // severity → 平台标签映射
}
```

- **去重是适配器职责**(需查平台侧状态):内建示例给最简策略(按标签+标题搜索 open issue,命中跳过);复杂策略(指纹比对/自动关闭过期单)由使用者自定义适配器或扩展配置;
- 配置加载、凭据注入、HTTP 调用全部发生在 `issues` 命令进程内,与测试执行进程隔离。

### 4.3 装配

```php
// Sink 注册表(与 PauseRegistry/DatasetRegistry 同构心智,但独立注册点):
final class SinkRegistry
{
    public function register(string $name, IssueSinkInterface $sink): void;  // 重名 430
    public function get(string $name): IssueSinkInterface;                    // 未知名 431
}
// bin/ws-http 装配时注册内建 GitLabIssueSink;编程使用者注册自定义 Sink
```

## 5. CLI:独立子命令(不挂 run)

```
bin/ws-http issues <report.json...> --sink <name> --config <qm.json>

行为:
  逐份读报告 → 无 issueIntent(没声明或 shouldCreate=false)→ 跳过(计数 skipped)
  → sink->publish(report) → 汇总 created/skipped/errors
选项:
  --dry-run            只打印将创建的内容(标题/labels/context 摘要),不调平台
退出码:0 = 全部成功(或无可建单);1 = 存在 errors(建单失败不回滚已建的,错误逐条列出)
```

- **`run` 命令零变化**(参数/退出码/渲染);issues 是**独立转换入口**,可重跑(报告在就能再发)、可人工审核(CI 先出 artifact,人工确认后跑 issues)、可在 CI 独立 stage 执行;
- 多报告聚合:多个 report.json 逐份处理,同一场景 id 跨报告去重由适配器策略承担(引擎不做跨文件状态)。

## 6. 错误码(400–499 引擎段追加)

| 码 | 含义 |
| --- | --- |
| 430 | Sink 注册重名 |
| 431 | 未知名 Sink(--sink 引用不存在) |
| 432 | Sink 配置非法(适配器自校验:必填字段缺失/格式错误;errors 中携带平台 API 失败不占此码) |

> 引擎段收尾:reporting 校验走 402(V24/V25);平台侧失败不进错误码体系(那是适配器的 errors 文本)。

## 7. 与既有设计的衔接

- design/14(Schema):reporting 场景级字段 + V24/V25(与 design/29 的 V20–V23 同批并入,编号接续);
- design/15(变量):reporting 求值用终态快照 + ${var} 同一替换器;secret 脱敏复用;
- design/16(Report):issueIntent 追加为可选字段(§3.2);finalize 求值点;CLI 增独立子命令(run 不动);
- design/16 §5.1(渲染器):同一"最小接口 + 消费端职责"决策模式;issues 命令的输出是纯文本摘要,不走渲染器注册表(它不是报告渲染,是操作结果反馈);
- design/23(Dataset):BatchReport 的每轮子 Report 各自携带 issueIntent(单轮失败各自判定);批次级不产生额外 intent(避免 50 条记录建 50 个单——去重归适配器,批次级聚合意图列扩展预留);
- design/25(工具谱系):触发条件记录——若未来 ≥2 个真实团队需要"场景引擎直接在建单闭环中运行",可评估 IssueSink 作为声明式工具的执行体;当前不做。
