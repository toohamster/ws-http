# 28 厂商接入层设计(VendorCatalog + ChatResult + 流式预研)

> 层归属:组件段(`Ws\Http\NanoGpt\`)+ Plugin 段既有实现归位认知;依赖单向:NanoGpt → Transport 层(Plugin),Transport 不感知编排。
> 背景:用户引入 `3rd/php-ai-sdk-main/`(PHP 8 + Guzzle 的多厂商 AI 连接库,**参考物,不入库——.gitignore 排除**)作对照分析,产出本设计。日期:2026-10-09。
> 定位:**使用工具库视角的多厂商接入**——用户接任意知名厂商不应改兼容代码;厂商知识集中标注,漂移时只改表。

## 1. 架构定位:Transport 层是独立的一层

**修正认知**(评审定调):NanoGpt 是**通用 GPT 编排工具**(agent loop/工具协议/沙箱/会话),**不是底层 agentDriver**。厂商/协议的 HTTP 对接是独立一层:

```
NanoGpt(通用编排:loop/工具协议/沙箱/会话)          ← 不感知厂商与协议
        ↑ 只依赖协议面
Transport 层(厂商 Driver:认证/端点/请求体/响应解析)
  ├─ OpenAiCompatible(现状:Plugin\OpenAI = 第一个实现,归位至此语义)
  │    └─ VendorCatalog:已知厂商档案表(本设计新增)
  └─ Claude 类(将来:协议级不同 → 新 Plugin,design/17 三件套坑位)
```

- 现状盘点:Plugin\OpenAI\Client 的 baseUrl/默认模型是**装配参数**(壳 bootstrap 时从 settings 传),**没有集中的厂商知识层**——使用者接 DeepSeek 得自己查 baseUrl;VendorCatalog 补这块;
- 多厂商两条路线(§8.2 评审结论延续):
  - **OpenAI 兼容系(DeepSeek/千问/Kimi/Moonshot/MiniMax…)**:换 baseUrl 即用,**零代码**;VendorCatalog 让"零代码"升级为"零查表";
  - **协议级不同(Claude 等)**:各写一个 Plugin(认证头/端点/响应结构整套不同),这是 design/17 既定扩展点,**本设计不实现**。

## 2. VendorCatalog(厂商档案表)

```php
namespace Ws\Http\NanoGpt;

/**
 * 已知厂商档案(静态知识层;档案非工厂——§8.2 约束延续:不做注册表/自动发现,
 * 接入路径不变,表只回答"这家服务的默认参数是什么")。
 */
final class VendorCatalog
{
    /** @return array<string, array{name: string, baseUrl: string, defaultModel: string, protocol: string}>
     *  protocol: 'openai-compatible' | 'anthropic'(后者将来接 ClaudeTransport) */
    public static function known(): array;

    /** 单家查询;未知 id 返回 null(不做兜底猜测) */
    public static function get(string $id): ?array;
}
```

- **初装 8 家**(php-ai-sdk 验证过的 baseUrl,含 Kimi 已换域名的新形态):

| id | name | baseUrl | defaultModel | protocol |
| --- | --- | --- | --- | --- |
| openai | OpenAI | https://api.openai.com/v1 | gpt-4o-mini | openai-compatible |
| deepseek | DeepSeek | https://api.deepseek.com/v1 | deepseek-chat | openai-compatible |
| qwen | 通义千问 | https://dashscope.aliyuncs.com/compatible-mode/v1 | qwen-turbo | openai-compatible |
| kimi | Kimi | https://api.kimi.com/coding/v1 | kimi-coding | openai-compatible |
| moonshot | Moonshot | https://api.moonshot.cn/v1 | moonshot-v1-8k | openai-compatible |
| minimax | MiniMax | https://api.minimax.chat/v1 | abab6.5s-chat | openai-compatible |
| claude | Claude | https://api.anthropic.com/v1 | claude-sonnet-4-6 | anthropic |
| orcarouter | OrcaRouter | https://api.orcarouter.ai/v1 | (项目验证源) | openai-compatible |

- **消费点**:① /init 的 baseUrl 提示(选适配器后展示档案默认值,回车即用);② 文档索引;③ **厂商改动只改此表**(漂移事实集中一处);
- 表内数据是**截至本设计的快照**,注明来源与日期;不承诺时效(使用者可覆盖);
- 不做的:不做自动探测/健康检查/版本协商(过度设计)。

## 3. ChatResult 响应 DTO(解析收归一处)

**现状问题**(对照 php-ai-sdk 的 AiResponse 发现):chat 响应的手解 `stdClass` 散在三处——Agent(loop 内取 content/tool_calls/finish_reason)、LlmCompactor(取 content)、ContextWindowProbe(取 content);`reasoning_content`(推理模型字段,N4 冒烟已见 deepseek 返回)**被静默丢弃**。

```php
namespace Ws\Http\NanoGpt;

final class ChatResult
{
    /** @param array<int, array{id: string, name: string, arguments: string}> $toolCalls */
    public function __construct(
        string $content,
        ?string $reasoningContent,      // 推理模型(deepseek-r1 系)字段,兼容不丢弃
        ?string $finishReason,          // stop / length / tool_calls…
        array $toolCalls,
        array $usage                    // ['prompt_tokens'=>int,'completion_tokens'=>int,'total_tokens'=>int]
    ) {}
    // getter 只读(PHP 7.4:传统构造,无 readonly/提升)

    /** 从 Response::body(stdClass)解析;结构缺失字段一律 null/[] 容错 */
    public static function fromBody(?object $body): self;
}
```

- 落位:组件层(与 Conversation 同层);**解析一处,消费三处**——Agent/LlmCompactor/ContextWindowProbe 改为 `ChatResult::fromBody($response->body)` 后读 getter;
- Agent loop 消费 toolCalls 的形态从 stdClass 链改为数组结构(回填逻辑不变,数据来源收口);
- **不替换** Plugin\OpenAI 的 Response 返回值(Breaking 面不动):fromBody 是静态解析入口,调用方自己接。

## 4. 流式预研(仅记录,不实现)

design/21 已定"不做流式,扩展预留"。php-ai-sdk 的 `parseStreamResponse` 是成熟参考,要点留档(将来 S 级需求输入):

- **SSE 解析**:按 `\r\n|\n|\r` 切行,**半行保持**(buffer 留最后一段);`data:` 前缀过滤;`[DONE]` 终止;
- **tool_calls delta 重装**(流式下工具调用分片到达):按 `index` 建 bucket,id/type/name **覆盖写**、arguments **追加写**;finish_reason 或 [DONE] 时一次性产出 ToolCall 集;
- **事件形态**:yield StreamChunk(content/done/reasoningContent/toolCalls)——与我们 Agent 事件流 Generator 心智同构,届时映射顺滑;
- 触发条件(同 design/26 Skill 模式):真实使用中出现流式需求再立项。
