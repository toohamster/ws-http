# 10 总体架构设计(PHP 7.4 重写)

> 本文是细化设计文档 11–17 的总纲:定义设计总则、core/functional/plugin 分层、模块边界、核心抽象与异常体系。各子系统细节见对应文档。

## 0. 设计总则

> "Simple things should be simple, complex things should be possible." — Larry Wall

全库的最高原则。它约束的是**使用者面对的复杂度曲线**,不是功能取舍:

1. **简单路径必须是最短的**:每个模块的最常用用法是一行代码/一个字段,零配置可跑;
2. **复杂能力不抬高简单路径的门槛**:高级功能的成本只由用到它的人支付;
3. **功能该实现就实现**:分级只决定复杂度放在哪一层呈现,不决定做不做;
4. **复杂度不可泄漏**:简单用法被迫接触高级概念即是架构缺陷。

评审标尺:每份细化文档(11–17)开头必须给出"简单路径"示例;功能按"核心(v1 用过或吃过亏)/ 扩展(明确场景)"标注呈现位置,无"不实现"档。

## 1. 三层架构:core / functional / plugin

三层是**面向不同使用者的独立复用资产**,依赖方向严格单向:

```
┌───────────────────────────────────────────────────────────────┐
│  plugin        三方系统适配(使用 core/functional)              │
│  对接 WordPress / OpenAI / 微信公众号…                          │
│  产出物 = 认证封装 + 端点定义 + 语义化方法                       │
├───────────────────────────────────────────────────────────────┤
│  functional    测试与编排能力(使用 core)                        │
│  断言器 · 表达式引擎 · 自动化引擎(任务/变量提取/执行/报告)        │
├───────────────────────────────────────────────────────────────┤
│  core          一个 cURL HTTP API 工具                          │
│  Request · Response · 配置 · Body · Method · 扩展契约(接口)      │
└───────────────────────────────────────────────────────────────┘
```

### 1.1 使用者画像与进入路径

| 使用者 | 动机 | 进入点 | 需要了解的范围 |
| --- | --- | --- | --- |
| PHP 开发者 | "我要发个 HTTP 请求" | `new Request()->get($url)` | 仅 core |
| 接口测试工程师 | "我要测 API、写场景" | Watcher / 场景脚本 + CLI | core + functional |
| 业务对接者 | "我要调 WordPress/OpenAI" | 对应 plugin 的语义化方法 | plugin 的门面方法(底层不需要知道) |
| 插件作者 | "接入新的三方系统" | PluginInterface 注册机制 | core API + 机制契约(见 design/17) |

### 1.2 层的硬规则

1. core 不依赖 functional/plugin 任何类;functional 不依赖 plugin;**扩展契约(接口)定义在 core**,实现在 functional/plugin;
2. plugin 之间互不依赖、互不感知;core/functional 不感知任何具体 plugin;
3. plugin 机制 = 注册契约 + 注入点,**不引入服务容器/事件分发/自动发现**(违反总则);
4. 所有内建实现同包分发(不拆 composer 包):`Ws\Http` core、`Ws\Http\Assert|Expression|Automated` functional、`Ws\Http\Plugin\*` plugin 内建件;第三方按同一契约注册自定义 plugin。

### 1.3 简单路径 × 分层(每层的一行入口)

```
core:       (new Request())->get('https://api.github.com')->body;
functional: Watcher::create($response)->assertStatusCode(200)->assertBody('IS_VALID_JSON');
functional: (new Runner())->run(ScenarioParser::parseFile('scenario.json'))->isSuccess();
plugin:     (new OpenAI($apiKey))->chat()->create('你好');   // 内部:core 请求 + Bearer 认证
```

## 2. 运行数据流(场景执行)

```
script.json
   │ ScenarioParser::parse (design/14)
   ▼
Scenario { meta, settings, variables[], steps[] }
   │ Runner::run (design/16)
   ▼
┌─ 每步 ────────────────────────────────────────────────┐
│ 1. ScenarioResolver.resolve(step, scope)   (design/15)│  ${var} 深替换
│ 2. Request 发送 → Response                 (design/11)│
│ 3. VarExtractor.extract(response, rules)   (design/15)│  提取 → VariableScope
│ 4. AssertionRunner.run(response, asserts)  (design/12)│  JSONPath + 操作符
│ 5. StepResult 收集(状态/耗时/断言/提取变量)            │
└───────────────────────────────────────────────────────┘
   ▼
Report { steps[], passed, failed, duration }  → CLI 渲染 + exit code
```

关键原则:表达式引擎是断言/提取的单一事实来源(design/13);Response 是唯一数据载体;引擎内部收集结果不抛异常(除解析失败)。

## 3. 命名空间与类清单

```
Ws\Http\                        # core:HTTP 工具 + 扩展契约
├── Request                     # cURL 引擎:配置 + send()
├── RequestOptions              # 配置值对象(wither)
├── HeaderBag                   # 大小写不敏感头集合
├── Response                    # 响应对象
├── Body                        # 请求体构造器
├── Method                      # HTTP 方法常量接口
├── RequestException / Exception
└── Contract\                   # 扩展契约(core 定义,供 functional/plugin 实现)
    ├── RequestFactoryInterface     # HTTP 工厂(mock/装饰器注入点)
    ├── CookieStoreInterface        # cookie 存储策略
    ├── ComparatorInterface         # 断言操作符
    ├── ExtractorInterface          # 提取 source(functional 内建 json/header;plugin 可扩展)
    └── PluginInterface             # plugin 注册契约(design/17)

Ws\Http\Expression              # functional:表达式引擎(design/13)
├── ExpressionEvaluator / Parser / ExpressionException

Ws\Http\Assert                  # functional:断言器(design/12)
├── Watcher                     # 流式断言门面
├── AssertionRunner / Assertion / AssertionResult
└── Comparison                  # 内建操作符集(ComparatorInterface 注册表)

Ws\Http\Automated               # functional:自动化引擎(design/14/15/16)
├── ScenarioParser / Scenario / Step(HttpStep|DelayStep)
├── Runner / StepResult / Report
├── VariableScope / ScenarioResolver / VarExtractor
├── AssertionRunner 编排 / MemoryCookieStore(默认实现)
└── AutomatedException

Ws\Http\Plugin\                 # plugin:内建三方适配 + 自定义注册入口(design/17)
├── PluginRegistry              # 注册机制(唯一公开入口)
├── OpenAI\…                    # 内建示例:认证 + 端点 + 语义化方法
└── WordPress\…                 # 内建示例
```

> 与旧代码对应:`Task/Body/Bootstrap` 重构为 `Scenario/Step/Runner`;`ARequest` 静态门面移除;`Watcher` 保留名称与链式语义。

## 4. 异常体系

```
\RuntimeException
└── Ws\Http\Exception                        # 基类:code = 错误码
    ├── Ws\Http\RequestException             # core:传输失败(errno + error + url)
    ├── Ws\Http\Expression\ExpressionException   # 语法/求值错误
    ├── Ws\Http\Assert\AssertionException    # 断言失败(仅 Watcher 流式抛;引擎收集不抛)
    └── Ws\Http\Automated\AutomatedException # 脚本解析失败等(无法继续才抛)
```
